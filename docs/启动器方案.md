# 通用编译 / 启动器：方案与路线

> 2026-10-21 · 目标：把「选文件 → 编译 → 跑起来 → 导出」做成一个点几下就能用的 macOS 应用，
> 像截图里那位开发者做的那样（他的界面已经是批量/通用移植的形态）。
> **结论：能做，而且上游已经给了七成。** 真正缺的不是流水线，是一层界面 + 每款游戏的"画像"。

## 2. 架构：SwiftUI 壳 + Python 流水线 + 事件流

```
┌──────────────────────────────────────────────┐
│  SwiftUI 应用（macOS 原生）                   │
│  ├ 文件选择：游戏文件夹 / DLC / prod.keys      │
│  ├ 设置：目标帧率、语言、导出目录             │
│  ├ 进度条：阶段名 + 步骤 + 计数 + ETA          │
│  └ 按钮：开始游戏 / 导出 IPA / 导出 .app / DMG │
└───────────────┬──────────────────────────────┘
                │  stdout: 一行一个 JSON 事件
                │  {"ev":"stage","name":"extract",...}
                │  {"ev":"progress","done":1234,"total":41062,...}
                ▼
┌──────────────────────────────────────────────┐
│  Python 流水线（上游脚本 + 我们的脚本）         │
│  build_ipa_from_nsp.py --progress json        │
│  make-mac-app.sh  /  sign-build.sh  /  ...    │
└──────────────────────────────────────────────┘
```

**为什么用 JSON 事件而不是抓控制台输出**：上游的进度本来是给人看的（`bar` 一行重画、`lines` 每秒一行）。
本轮给它加了 `--progress json`（一行一个 JSON 对象），GUI 只要读一个流就能画进度条、显示阶段名和计数，
**不用去正则匹配控制台文本**——上游的文本格式会变，JSON 事件是契约。

**为什么用 SwiftUI 而不是 Electron/Tauri**：机器上已经有 Xcode；SwiftUI 零额外运行时、原生文件选择器、
`NSOpenPanel` 存目录、进度条都现成；打包流水线本来就得靠系统的 Python + Xcode。
（Electron 会多带一个 200 MB 运行时，Tauri 要装 Rust，都不划算。）

## 4. 真正的门槛：每款游戏的"画像"

上游给了两条路：

1. **有画像**（16 款）：`dm/games/<id>/` 里是 title ID、已知 build、代码模块、RomFS 标记、
   **内存分配**、NVN 驱动表、着色器表、链版本。全自动，直接能出可玩的包。
2. **没画像**：`build_ipa_from_nsp.py` 先写一份 **survey**（模块、SDK、引擎、容器、重写点、
   导入与宿主钩子的对比），再用 `profile_guess.py` 猜一份**临时画像**（图形 API、模块、着色器来源、
   内存分区、SDK/引擎预设），必要时在 Mac 上跑一次**堆检查**（几秒钟，读游戏自己的堆请求），
   然后出包——**但这个包可能起不来**。

**起不来之后是人工活**（上游的 `docs/agents/` 就是干这个的：二进制普查、宿主 bring-up 失败目录、
图形、调试配方）。BotW 就属于这一类：我们的 1.9.0 画像里的**内存分配**（4 GiB 池 / 6 GiB 地址空间）
就是 bring-up 时量出来的——游戏带 DLC 时会把堆撑爆，Switch 版的 `app_pool` 给不够。

> **所以启动器能做到的是"批量"（一次编译多款有画像的游戏），不是"通用"（任意游戏自动可玩）。**
> 后者是移植工作，不是打包工作。截图里那位开发者界面上的「Mac 游戏代码：已就绪 · 1.9.0」
> 正是这个意思——他的"代码"那一栏是**每款游戏单独准备好的移植成果**。

**没有「固件」这一项**：上游流水线根本没有固件这一步（只认 `prod.keys`），所以那一行去掉了，README 里留了一句说明。

**一个游戏目录里可能有多个更新包、多个 DLC**（2026-10-21）：这一项重做了。原来是把所有文件名用 `, ` 拼成一行放右边，而那一行是单行截断的，所以文件一多就看不全——只能看到头尾，中间被砍掉，也看不出有几个。

现在管线直接吐出结构化的文件信息（`title_id` / `name` / `label` / `path`），界面按组显示：

| 情况 | 显示 |
|---|---|
| 0 个 | `—` |
| 1 个 | 原地显示文件名（和以前一样） |
| 多个 | 右边显示「N 个」+ 展开箭头；展开后每个文件一行：**标题 ID**（强调色等宽，永远完整）+ 去掉 ID 的名字（干净、不重复），悬停给完整路径，可复制 |

标题 ID 单独一列是关键：ID 固定 16 个字符、永远放得下，名字再长再乱也不影响它可读。超过 10 个时只列前 10 个并写明「还有 N 个」。

**Mac 游戏窗口的三个毛病**（2026-10-21，`dm/host/front_mac.m`）：非圆角、最大化键无效、不能拖动缩放。查下来是**两个独立的 bug**：

1. **窗口自己的鼠标事件被吞了**。原来用 `addLocalMonitorForEventsMatchingMask:` 监听左键/右键/移动，把落在窗口里的事件一律 `return nil` 吞掉。交通灯、标题栏、缩放手柄**都属于这个窗口**，于是按下事件到不了 AppKit：最大化键按了没反应，窗口拖不动也缩不了。
   改成**让内容视图自己处理鼠标**（`DmGameView` 的 `mouseDown:` / `mouseDragged:` / `mouseUp:` / `rightMouse*` / `mouseMoved:`），不再用监视器。窗口自己的部件**根本不会到达内容视图**，所以自然就能用了；画面里的触摸模拟（左手键 = 屏幕上一根手指）也照旧。
   顺带：Cmd 组合键（Cmd+Q 退出、Cmd+M 最小化）以前也被吞掉，现在放行了。

2. **画面把窗口的圆角盖住了**。窗口本身是圆角的，但内容（Metal 层直接画进窗口表面）没有被窗口的形状裁剪，方角把圆角盖掉了。修法是把内容层裁成同样的半径（`masksToBounds` + `cornerRadius` 10 + `kCACornerCurveContinuous` 连续曲率，和 macOS 26 系统窗口同款）。

   标题栏同时设成**透明**（`titlebarAppearsTransparent = YES`）：内容视图本来就覆盖整个窗口（标题栏浮在它上面盖住顶部 32 点），标题栏透明之后，窗口的顶角就是内容的顶角，于是**标题栏顶部圆角、标题栏与内容的交界是一条直线、内容底部圆角**——整个窗口看上去是圆的。

   > 四个角的裁剪曲线实测：最外一行切掉 7 pt，14 px（7 pt）内收到 0，上下左右完全对称。

> 验证方式：往窗口投递合成鼠标事件（`NSApp.postEvent`），看**哪个处理器收到它**——画面按下/拖动/抬起 → 视图收到（触摸模拟正常）；交通灯、标题栏、右下角 → 视图收不到，归窗口所有。

> **子模块钉在 `bc5815a` 的原因**：上游已经重构了这些文件（`dm/host/dm_i18n.c` 都被挪走了），补丁**不能**应用到新的 HEAD。升级子模块 = 重新 rebase 补丁 + 重新验证构建。

## 6. 诚实的风险

| 风险 | 说明 |
|---|---|
| **首次编译 30–60 分钟** | 着色器翻译是瓶颈。缓存命中后 ~10 分钟。UI 必须能让人安心等着看进度——这正是 JSON 事件流的价值 |
| **磁盘** | 每个包 15–17 GB，加上解包和缓存，一款游戏轻松占 50–80 GB。导出目录要让人自己选 |
| **每款游戏仍需人工 bring-up** | 见第 4 节。启动器能把"有画像的游戏"批量自动化，不能把陌生游戏变成可玩游戏 |
| **模拟器帮不上忙** | Apple 把模拟器 SDK 里的 Metal 4 拿掉了（真机 113 条声明 vs 模拟器 1 条）。iOS 端只能真机验证，Mac 端才是能自动验证的那条路 |
| **签名是手工活** | 同事的包只能给未签名版 + 让他自己重签。要直装就得把对方 UDID 加进开发者账号 |
| **上游脚本会变** | 我们改了 `build_ipa_from_nsp.py`（加 json 模式）。以后同步上游要留意这个改动 |
